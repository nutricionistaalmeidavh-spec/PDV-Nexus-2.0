# P2–P4 — Modularização do restaurante, React e homologação automatizada

Base: PR #26 (`ac6310d`), stack self-hosted R$0, SQLite WAL local, Node e React/Vite open source.

## P2 — Restaurante e KDS

- `table-service.mjs`: leitura, cadastro/renomeação de mesas, abertura idempotente e transferência, com transação.
- `modifier-service.mjs`: adicionais por produto, consulta e gravação auditadas, sem alterar snapshots anteriores.
- `kitchen-service.mjs`: tickets por UUID persistente da linha, regra única de transições PENDING → PREPARING → READY → SERVED, estados CANCELLED, revisão otimista e reenvio idempotente.
- `restaurant.mjs`: fachada de compatibilidade; mantém `restaurantRead`, `restaurantWrite` e `dispatchKitchenTickets` exportados para consumidores existentes.
- Continuam válidos os bloqueios de cancelamento quando a produção avançou ou existem pagamentos e a autorização gerencial da PR #24.

**Regressão:** `test_p2_restaurant_modules.test.mjs` testa o domínio e a API real, duas linhas com IDs de ticket distintos, conflito de revisão, retry sem duplicar, impedimento de cancelamento em preparo, mesa ocupada e nenhum ticket perdido.

## P3 — React isolado por responsabilidade

| Arquivo | Responsabilidade |
|---|---|
| `UIPrimitives.jsx` | componentes compartilhados de apresentação (sem fonte própria de dados) |
| `CommerceScreens.jsx` | vendas, produtos, pedidos, checkout, login |
| `RestaurantScreens.jsx` | mesas, garçom, KDS, caixa e apresentação de rateio |
| `AdminScreens.jsx` | primeiro acesso, relatórios, usuários, impressão e exportação |
| `navigation.mjs` | inventário de itens e visibilidade por papel (a segurança real continua no backend) |
| `useOperations.jsx` | atualização de dados do host, polling de KDS e prevenção de comandos concorrentes |

- `App.jsx` compõe as telas, estado e rotas existentes; deixou de declarar telas e formulários extensos.
- Não foi criada segunda base de estados: o SQLite e a API local continuam fontes oficiais. Estado React só representa sessão, interface, visibilidade e projeções consultadas.
- Não há novas libs, serviços de IA ou cloud; nenhuma alteração de chaves, migrations, URLs ou assinaturas.
- `test/navigation.test.mjs` verifica papéis cashier/admin/garçom/KDS e IDs únicos de navegação. Testes atuais de modelo/React e Playwright verificam paridade do comportamento de telas.

## P4 — Evidências automatizadas e homologação

- `qa-react-browser.mjs`: fluxo com SQLite real, cadastro com consulta KDS indisponível, pagamentos em três tamanhos, fechamento único, reinício, backup e host offline.
- `qa-parity-browser-v2.mjs`: fluxo completo de catálogo, adicionais, estoque, caixa, mesa, divisão, venda, cozinha, delivery, unidades e periféricos simulados.
- Captura **cada aba visível** em desktop 1440×940 e mobile 390×844.
- Grava vídeos independentes desktop/mobile, `journey-manifest.json` listando telas/arquivos e falhas de JavaScript; compara paridade de navegação, verifica scroll horizontal em telas mobile.
- Actions armazena `artifacts/qa/` com screenshots, vídeos WebM e manifesto por 14 dias.
- Gates: `npm test` (domínio + SQLite + API), `npm run ui:test`, build React, sintaxe JS, CI Windows/Linux, Windows diagnostics, Playwright e instalador Windows unsigned, **sem publicação**.

### Limites de homologação

A execução em runner Windows verifica instalação descartável, não funcionamento em impressoras físicas de um cliente. Os testes de comunicação serial/TCP, gaveta, leitura real de balança, impressora ESC/POS específica, certificado LAN de cliente e múltiplos dispositivos físicos precisam de bancada e aceitação específica. Não tratar periférico simulado como homologado fisicamente.

### Integração e rollback

Esta PR depende da #26 (P0/P1) e deve ser integrada depois dela. Se o branch base mudar, revalidar os gates no novo HEAD antes de squash. Não realizar merge na main nem publicar release sem autorização. Reversão é por commit; o esquema SQLite permanece inalterado.
